# The console demo (static build on a recording)

`docs/demo/` is the real console, built for static hosting. The project page embeds it and the board on that
page follows it. This file says exactly what is real in it and what is not.

## What it is

- The same React app as the live console (`services/ws7-dashboard/app`), built with `npm run build:demo`
  (`vite build --mode demo`, output `docs/demo/`). The normal build contains none of the demo code or data
  (`import.meta.env.VITE_DEMO` is a compile-time constant).
- Every `/api/*` call is answered in the browser by `src/demo/adapter.ts` from `src/demo/fixtures.json`.

## What the data is

The first scenario is a **recording of a lab run** on a local Docker stack: 50 alarms, 100 events, 3 incidents, 14 assets, the graphs
and verified evidence packages, and the generated incident and NIS2 reports (each stage, each language) for the
replayed attack's own alarms. The attack traffic is generated by `tools/console_tour_traffic.py` with
documentation-range addresses (RFC 5737). It is lab data, not a real attack, and the console says so
(the **Demo** chip in the top bar).

## The second scenario: AI agent to OT (generated, not recorded)

Pick it in the demo bar's scenario list, or open `docs/demo/?scenario=ai-ot`. The project's headline story: an n8n
webhook exposed out of hours, an agent tool call carrying a prompt-injection indicator that reaches a non-allowlisted
domain and reads credential material, then a Modbus/TCP write outside the PLC address range.

- **Input is synthetic**: the evaluation twin's deterministic raw records (`eval/twin/scenario.py`, seed 7).
- **Everything after the input is the production code**, run in-process on the in-memory bus by
  `tools/build_ai_ot_fixtures.py`: WS-2 normalize, WS-4 detect, WS-5 triage, WS-8 correlate, WS-9 resolve, WS-3 index.
  The alerts, incidents, entity graphs, hash-chained evidence packages, incident reports and NIS2 drafts (EN and DE)
  are the answers of the real WS-3 handler (`triage_api.py`) over that store. Nothing is written by hand.
- **Generated rather than recorded**: it did not run on a live Docker stack (no Redis, OpenSearch or collectors), so
  the alert and event lists are shaped like the console's OpenSearch answers by the script (same selections as the
  nginx proxy: alerts with a `rule_title`, AI verdict docs prefixed `ai-`). Inventory, users, audit and service
  health are the lab recording's, unchanged.
- **AI triage is the stub backend** (`engine: stub`, no model); the console shows the backend per verdict.
- **Replay is 12x faster** than the twin's 60 s between steps (`meta.timeScale`); the evidence blocks keep the
  original times. The badge in the demo bar says so in plain sight ("12x faster · stub AI"), not only in its tooltip. The 2.5 s and 5 s stage delays are estimates, as in the lab scenario.
- **What it does not show**: the two incidents share one host (`10.20.0.50`) and one actor (`ot-engineer`); the
  incident graph joins on shared entities and is order-blind (`eval/SCORECARD.md`). It is not IT-to-OT correlation
  across different hosts and not a causal graph. The web-proxy step has no parser (dead-lettered), and the Modbus
  read that follows the first write raises no alarm: seven alarms, as in the twin.
- **The project page** (`docs/index.html`) has two replay buttons: "Replay the attack" (key `R`, the recorded lab
  scenario) and "Replay the AI-to-OT chain" (key `A`). The second posts `scenario: "ai-ot"` to the embedded console. While it
  plays, the board tag and the terminal caption read "synthetic input, real pipeline output" instead of "recorded
  lab data", and WS-1 stays "ready" on the board (no collector ran: raw records are injected). The board shows the
  newest three rows; the page receives 7 `alarm` messages and 2 `incident` messages (7 and 5 alarms).
- Regenerate with `python tools/build_ai_ot_fixtures.py`; `tools/test_build_ai_ot_fixtures.py` fails when the
  committed `fixtures-ai-ot.json` is stale (it ignores only wall-clock stamps).

## What is edited

- **Timestamps are shifted** so the recording reads as "just now" (history sits just before page load; the replayed
  attack is stamped from the moment you press Replay). Nothing else in the data is altered.
- The audit trail is the **last 40 entries** of the recorded one (the earlier ones are test-harness noise).

## What behaves differently from the live console

- **Writes are in-memory**: acknowledging an alarm, adding a device, creating or disabling a user, switching a rule.
  They look right and are gone on reload. There is no sign-in; the session is a fixed admin.
- **MFA enrolment is off** and **Prometheus is not part of it** (the Operations health panel says so).
- **Reports** exist only for the replayed attack's own alarms and incidents; other alarms get a plain note.

## The replay

Before "Replay the attack" the attack is **hidden**: the banner is quiet and the incident list shows only earlier
runs. After it, events appear at their recorded offsets; the alarms and the incident appear after an approximate
processing delay (2.5 s and 5 s). **The real stage latencies were not recorded**, so those two delays are
estimates, and the demo says so in its tooltip. The page that embeds the demo can start the replay and receives
`alarm`, `incident`, `verified` and `replay-done` messages (`postMessage`, same origin).

## Re-recording the fixtures

```sh
cd tools/console_e2e && npm install
node close_alarms.mjs                                     # earlier lab alarms closed -> quiet start
python ../console_tour_traffic.py 127.0.0.1 5514 203.0.113.50   # one fresh attack, wait ~45 s
node record_fixtures.mjs 203.0.113.50                    # writes src/demo/fixtures.json
cd ../../services/ws7-dashboard/app && npm run build:demo
node ../../../tools/console_e2e/demo.mjs                 # 38 checks against docs/demo (both scenarios, EN and DE)
node ../../../tools/console_e2e/pages.mjs                # 75 checks against docs/ (project page, both replays, EN/DE, phone width)
```

Needs a running stack with RBAC and the three test accounts (see `tools/console_e2e/README.md`). Local lab
stacks only: these scripts create users, add devices and send unauthenticated UDP syslog.
